## ADR-001: 存储层用 AList REST API 还是 WebDAV？

**日期**：2026-07-01

### 上下文

视频资源通过 AList/OpenList 挂载多种网盘（115、天翼云等）。白皮书最初设计的核心容灾机制"双保险检索"依赖文件 Hash（SHA1）进行跨盘无感认亲。需要确定 Go 后端与 AList 的交互协议。

### 讨论过程

1. **最初方案**：直接用 AList REST API（`/api/fs/get`, `/api/fs/link`）
2. **用户反馈**：改用 WebDAV（`/dav/`），因为实际使用的是 AList 暴露的 WebDAV 服务
3. **技术调研发现**：
   - WebDAV 协议（RFC 4918）**没有标准的文件 hash 属性**
   - AList REST API 的 `/api/fs/get` 能返回 `hash_info.sha1`（115 等网盘原生支持）
   - WebDAV 的 302 直链**是可以工作的**（通过 PotPlayer 实测验证，AList WebDAV 内部做了重定向）

### 决策

**不二选一，而是用 Go interface 抽象出 `StorageProvider`，同时提供两种实现**：

- **AList REST API 实现**：完整能力（hash + 直链 + 浏览）→ 自己用
- **WebDAV 通用实现**：基本能力（浏览 + 直链，无 hash）→ 给别人用

### 理由

- AList REST API 是唯一能拿到 hash 的方式（除非直接对接 115 原生 API，复杂度太高）
- WebDAV 对外兼容性更好（不依赖 AList，任何 WebDAV 服务器都能对接）
- 接口抽象的开发成本极低（一个 interface + 两个 struct），扩展性收益巨大
- 无 hash 时仍有路径+文件大小兜底，白皮书的容灾机制不会完全失效

### 状态

✅ 已确认

## ADR-002: 115 网盘的 302 直链能否工作？

**日期**：2026-07-01

### 上下文

白皮书核心设计之一是"视频流量直接走网盘→用户 PAD，完全不占用服务器带宽"。这依赖 302 重定向到网盘直链。

### 调研结论

**115 是 AList 中的"强制代理"驱动**。115 原始下载 URL 有 IP/Cookie 绑定限制，客户端无法从 115 服务器直接下载。无论走 AList REST API 还是 WebDAV，视频流量都必须经过 AList 代理。

### 决策

接受 115 的代理现实。对于家用场景（PAD 和服务器在同一局域网），AList 代理消耗的是内网带宽（通常 1Gbps+），不影响使用体验。其他网盘（如天翼云）如果支持直链，AList 会自动返回直连 URL，此时 302 方案天然生效。

Go 后端的实现**不关心这个差异**——始终做 302 重定向到 StorageProvider 返回的 URL，AList 已经根据驱动类型处理好了。

### 状态

✅ 已确认

## ADR-003: 多存储源 vs 单存储源

**日期**：2026-07-01

### 上下文

用户考虑过是否需要支持同时配置多个存储源（多个 WebDAV、多个 AList），以及跨源聚合的虚拟表。

### 讨论过程

- AList 本身就是多存储抽象层：在一个 AList 实例中可以挂载 115、天翼云、夸克等，通过路径前缀区分
- 真正需要多存储源的场景是：**同时用 AList + 独立 WebDAV**，或者**多个 AList 实例**
- 多源聚合（虚拟表）增加大量复杂度

### 决策

**MVP 单源**（`settings` 表存一个当前存储源配置），**预留多源扩展性但不实现**：

- 当前 `episodes` 表不加 `source_id` 字段
- 未来需要多源时：
  1. 新增 `storage_sources` 表
  2. `episodes` 表加 `source_id` 列（`ALTER TABLE`，不影响已有数据）
  3. `StorageProvider` interface 不需要改
- `StorageProvider` 接口本身就是面向多源设计的，每个源一个实例

### 理由

单个 AList 实例已经能挂载多个网盘，覆盖绝大多数场景。过早引入多源聚合会显著拖慢 MVP 进度，且大概率在很长时间内用不到。

### 状态

✅ 已确认

## ADR-004: 业务配置存数据库而非环境变量

**日期**：2026-07-01

### 上下文

最初设计将 AList URL、Token 等配置放在环境变量中。

### 决策

**只保留两个启动必需的环境变量**（`SERVER_ADDR`、`DB_PATH`），所有业务配置存 `settings` 表，由 Admin 面板管理。

### 理由

- 存储源配置需要在运行时修改（换地址、更新 Token），重启服务不可接受
- Admin 面板是天然的配置管理入口
- 对于 2C2G Docker 部署场景，减少环境变量数量也降低了部署复杂度

### 状态

✅ 已确认

## ADR-005: 附件通用化

**日期**：2026-07-01

### 上下文

白皮书定义了 `pdf_relative_path` 字段，限定为 PDF 格式。

### 决策

改为 `attachment_json`（TEXT 类型，存 JSON 数组），支持多类型附件：

```json
[
  {"type": "pdf", "name": "练习册.pdf", "path": "/115/课程/练习册.pdf"},
  {"type": "worksheet", "name": "课后练习.docx", "path": "/115/课程/练习.docx"},
  {"type": "audio", "name": "听力材料.mp3", "path": "/115/课程/听力.mp3"}
]
```

### 理由

学习资料不只有 PDF——可能有 Word 文档、音频材料、图片等。JSON 数组提供了最大灵活性，且不需要额外的关联表。

### 状态

✅ 已确认

## ADR-008: 工作负载拆分与字幕解耦

**日期**：2026-07-01

### 上下文

原始设计中，视频转录（Whisper）、AI 内容生成（DeepSeek）都在本地台式机一气呵成，并且字幕生成是课时入库的强前置条件。但这带来了几个问题：
1. **强耦合**：很多视频已在网盘，如果不立刻开台式机跑字幕，连简单的课时目录都无法在后台建立。
2. **灵活性差**：如果对 AI 题目不满意，必须重新跑本地脚本来调用 DeepSeek，无法在 Admin 网页端操作。
3. **安全/配置问题**：DeepSeek API Key 需要散落在台式机上。

### 决策

1. **分离重负载与轻负载**：
   - **重负载 (Whisper)**：保留在台式机，吃 GPU 算力。生成的 `.srt` 带有原始 metadata（如 AList 路径作为兜底匹配）。
   - **轻负载 (DeepSeek)**：迁移到 Go 服务器端。API 调用是纯网络请求，不消耗 2C2G 资源，且方便通过 Admin 面板触发。API Key 集中在 `settings` 表管理。

2. **解耦字幕生产与课时入库**：
   - 台式机将生成的 `[hash].srt`（附带 metadata）推送到服务器上的特定目录（如 `data/subtitles/`），作为独立的资产仓库。台式机可定期备份。
   - Admin 面板**随时**可以导入网盘视频建立课时（`episodes` 表），哪怕没有字幕。
   - 系统通过 `file_hash` 或 `original_relative_path`（metadata 兜底）去字幕仓库认亲。
   - 有字幕的课时，Admin 可点击触发 DeepSeek 生成 AI 探险卡和题目。如果缺字幕，流程在此阻断，但基础播放不受影响。

### 理由

极大地提升了日常运维的灵活性。课时上架（轻量操作）与字幕生成（重度操作）被完全拆解成两条互不阻塞的流水线。同时解决了 AI 重新生成的痛点。

### 状态

✅ 已确认
