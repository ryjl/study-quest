# 过程复盘:播放器 ESC 分层 —— 一个一行代码的 bug 为什么花了一整个 session

> **本文档是过程复盘**(和 `flutter-esc-layering.md` 的技术主线互补)。那份讲「根因是什么、
> 怎么修的」;本份讲「**为什么定位花了这么久、走了什么弯路、流程上能怎么改进**」。写给复盘
> 报告,也写给下次别再这么慢。
>
> 一句话总结:**根因是一行 Intent 绑定错误,但诊断被 mumu 模拟器的三重观测障碍层层误导,
> 中间还得出过「不是 app bug」的错误结论,直到用户坚持真机 TV 也复现才扭转。耗时 ≈ 一个
> session,其中真正定位根因只花了读 Flutter 源码的几分钟。**

---

## TL;DR(给复盘报告的要点)

- **问题本身的难度:低**。根因是 escape 绑了框架 `DismissIntent`,被 `MaterialPageRoute`
  的 `_DismissModalAction`(maybePop)抢走。一行绑定错误 + 一个新的分层状态机,代码改动
  70 行。
- **耗时的真实来源:诊断环境不可靠 + 方法不得当**,七三开。
  - 七成是 mumu 模拟器的三重观测障碍:logcat 丢 Dart 日志、`adb input keyevent` 注入的键
    和真实按键走不同路径、文件日志写不进(scoped storage)。三个观测手段全失效,导致
    「看不见 app 内部」,只能瞎猜。
  - 三成是方法问题:没第一时间验证工具可信度;发现矛盾(用户说退出、我测不退出)没立刻
    怀疑测试方法,而是反复让用户手测确认。
- **最严重的判断失误**:一度下结论「ESC 不是 app bug,是 mumu 模拟器特有行为」,还写进了
  踩坑文档。**这个结论是错的**,根因是手机没有 ESC 键、只测了系统返回键(KEY_BACK 路径),
  代表不了 TV 遥控器的 ESC。直到用户坚持「真机 TV 上也有问题」才推翻。
- **转折点全是用户驱动的**:「你能靠谱点吗」(停止反复手测)、「UI 这么难吗」(促使重新
  审视方法)、「装在 TV 上还是有问题」(推翻错误结论)。AI 自己没能及时纠偏。
- **教训(流程层面)**:① 模拟器怪相当环境问题查,别当 app bug 修;② 按键类回归必须上
  真机;③ 发现矛盾先怀疑工具;④ 不要在观测手段不可靠的环境里盲目改代码。

## 时间线 + 决策点

### 阶段 1:接手 + 搭测试框架(方向对,但埋了隐患)

起点是交接文档 `docs/handoff/player-esc-and-test-framework.md`,说 ESC 分层回归「根因未
定位」,并提供了 adb+uiautomator 的测试框架原型,建议先固化框架再诊断。

- ✅ 方向对:先搭框架、用框架自动复现,符合交接文档建议。
- ⚠️ **隐患(当时没意识到)**:固化框架时发现交接文档原型有 bug(`content-desc` 属性正则
  用 `\w+` 不匹配连字符,导致 Flutter 文字全读不到;视频播放态 dump 持续失败)。交接文档
  说「框架已验证可行、能读到中文」,实测根本读不到 —— **交接文档的「已验证」不可全信**。

### 阶段 2:被 mumu 三重观测障碍困住(耗时的主因)

诊断 ESC 需要抓「按 ESC 后 app 内部走了哪条代码路径」。但 mumu 上三个观测手段全失效:

1. **logcat 丢 Dart 日志**:连已知的 `print` / `debugPrint` 都不显示在 logcat(对比真机
   一抓就有)。导致「加日志看路径」这条路完全走不通。
2. **`adb input keyevent` 注入的键 ≠ 真实按键**:adb 注入的 ESC(111)进 Flutter KeyEvent
   系统(走 DismissIntent 关控件,不退出);mumu 真实 ESC 键不进 KeyEvent、直接 pop 退出。
   **两者表现相反**。这是最致命的陷阱:我用框架测 ESC「不退出」,用户按真实 ESC「退出」,
   结论打架。
3. **文件日志写不进**:想绕过 logcat 把日志写 `/sdcard`,被 Android 11+ scoped storage
   拦;app 内部目录 `/data/data/...` 又要 root/run-as,mumu 的 adb shell 不是 root。

三个手段全挂 → 看不见 app 内部 → 只能靠屏幕行为 + 瞎猜。

### 阶段 3:错误结论「不是 app bug」(最该避免的重蹈)

基于「手机(P30Pro)系统返回键分层正常」,下结论:**ESC 退出是 mumu 模拟器特有行为,不是
app bug,不要为 mumu 改 app 代码**。还写进了踩坑文档、提交了。

**错在哪**:手机没有 ESC 键,只测了系统返回键(`KEY_BACK` 路径)。而 ESC(`KEY_ESC`)走
的是另一条 action 链(Shortcuts→DismissIntent)。**用返回键的「正常」推断 ESC 的「正常」,
是错误类比。** 当时被 mumu 的怪相带偏,急于给「不可复现」找解释,跳到了「环境问题」这个
省力的结论。

### 阶段 4:试了多条死路(被错误前提带偏的代价)

在「mumu 特有」的错误前提下,试的修复都是对着 mumu 这个错误目标:

- `AndroidManifest` 加 `enableOnBackInvokedCallback="true"` —— mumu 是 API 32,该属性被
  忽略,无效。
- `MainActivity` override `onBackPressed` + MethodChannel 转发 —— 加 `Log.d` 验证,mumu
  上真实返回键根本不调用 `onBackPressed`,是死代码。
- 用 `diag_esc.js`(adb 发键)诊断 —— adb 注入 ≠ 真实按键,结论不可信。

**全部失败。每条都改了代码、构建、装包、让用户手测,然后回退。** 这是反复折腾用户、被
吐槽「你能靠谱点吗」的直接原因。

### 阶段 5:转折 —— 用户坚持真机 TV 复现(推翻错误结论)

用户把 app 装到真机 TV(TCL m7642),反馈「TV 上还是有问题」。这直接证伪了「mumu 特有」
的结论 —— **ESC 退出是真 bug,代码有问题**。

这时才回头查 Flutter 源码(早该做的事)。读 `routes.dart:1198` 几分钟就找到根因:
`MaterialPageRoute` 注册了 `DismissIntent→_DismissModalAction`(maybePop),escape 绑
DismissIntent 会被抢。**根因定位本身极快,慢的全在前面绕弯。**

### 阶段 6:修复 + 验证 + 收尾

- 修复1:escape 改绑自定义 `_ToggleControlsIntent`,杜绝被 ModalRoute 抢。
- 修复2:用户明确需求(全屏 ESC 不要直接退出,先唤出控件),加了 YouTube 式分层
  `_applyEscLayering`。
- 验证:mumu 确认 ESC 不退出 ✓;手机确认返回键正常 ✓;全屏内部分层未在真机 TV 验证
  (TCL 装包被封)。

> 注:TCL TV 的 `pm install` 被系统封(`install_switch_flag:0`),改 prop/settings/session
> 都绕不过,只能 U盘/当贝市场侧载。真机 TV 调试成本高,这也是验证不完整的原因。

## 流程教训(写进复盘报告)

1. **观测手段不可靠时,先解决「能不能看见」,再改代码**。在 mumu 这种 logcat 丢日志、
   adb≠真实按键的环境里盲目改代码,等于蒙眼修车。应该先花 10 分钟确认「我加的日志能不能
   出来」,出不来就换环境(真机),不要硬猜。
2. **发现矛盾,先怀疑工具和方法,不要反复确认结论**。「用户说退出 / 我测不退出」这个
   矛盾是工具不可靠的铁证,本应立刻怀疑 adb 注入 ≠ 真实按键。实际却反复让用户手测七八次
   去「确认」。这是把用户当人肉测试器、且浪费时间的根源。
3. **不要用「省力的结论」跳过验证**。「是模拟器/环境问题,不是 app bug」是最省力的解释,
   但没经验证就采信,导致整个阶段 4 全是无效劳动。环境问题要靠「真机也复现/不复现」来
   证实或证伪,不能靠「我想不通,大概是环境」。
4. **不同键 ≠ 同一条路径**。系统返回键(KEY_BACK)和 ESC(KEY_ESC)在 Android/Flutter
   里走完全不同的处理链。用其中一个「正常」推断另一个「正常」是错的。诊断要明确「测的
   是哪个键、走哪条路径」。
5. **真机 logcat 是诊断 Flutter/Android 交互的正道**。同一套日志,真机一抓就有,mumu 一个
   都出不来。模拟器适合快速迭代 UI,不适合诊断系统级交互(按键/返回/back 通道)。
6. **交接文档的「已验证」要复核**。本次交接文档说测试框架「已验证能读中文」,实测因正则
   bug 读不到。接手时对关键前提做最小复核,能省后面大量弯路。

## 给复盘报告的「省思」素材(可选)

- AI 在长时间诊断中容易陷入「确认偏误」:一旦倾向「mumu 特有」,后续所有现象都被往这个
  方向解读,直到外部输入(用户反馈 TV 复现)强制纠偏。
- 用户的几句直白反馈(「你能靠谱点吗」「UI 这么难吗」)是这次最重要的纠偏信号,AI 应该
  把这类反馈当作「方法可能错了」的强提示,而不是情绪。
- 真正的根因(一行 Intent 绑定)和付出的时间严重不成比例 —— 慢的不是问题,是诊断过程。
  这类「代码简单、诊断难」的 case,价值在于把诊断方法沉淀下来(见上方教训),避免下次
  同类问题再花一个 session。
